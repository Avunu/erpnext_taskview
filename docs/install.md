TaskView for ERPNext installs like any Frappe app. Two things are specific to it: the assets have to be built, and the install points the site's customer portal at `/projects`.

## Before you start

- A bench with Frappe v16 and a site that already has ERPNext installed.
- Node and yarn on the bench machine. The project is built with Node 24 in CI.
- A System Manager login on the site.

> [!IMPORTANT]
> Install TaskView after ERPNext. The portal page at `/projects` replaces ERPNext's own `/projects` page, and Frappe resolves website pages across the installed apps in reverse install order.

## Install

Run these from the bench directory. `<SITE_NAME>` is your site, for example `site1.example.com`.

```bash
bench get-app https://github.com/Avunu/erpnext_taskview --branch version-16
bench --site <SITE_NAME> install-app erpnext_taskview
```

The `version-16` branch is created by the first release. Until then, get the app from `main` instead:

```bash
bench get-app https://github.com/Avunu/erpnext_taskview --branch main
```

`bench get-app` builds the app's assets. If you install from a checkout that was not built that way, build them yourself:

```bash
bench build --app erpnext_taskview
```

The build matters more than usual here. Frappe's build runs each app's `build` script from its `package.json` (and runs `yarn install --frozen-lockfile` first when the app has no `node_modules`). For this app that script builds the Task View and timer dock bundles and the portal, then updates `sites/assets/assets.json`. The portal's page, `erpnext_taskview/www/projects.html`, and its files in `erpnext_taskview/public/portal/` are generated by that build and are not in the repository, so without it `/projects` has nothing to show.

## What installing sets up

Installing the app does these things on its own:

- It adds the custom fields and property settings listed in [Configuration](configuration.md#what-the-app-adds-to-your-site), including **Budgeted Hours** on Project, and makes Task View the default list view for Task and Project.
- It registers the `/projects` portal, a **Projects** entry in the portal menu for users with the Customer role, and a redirect from the old `/project` list to `/projects`.
- It sets up the portal in your site's settings:

| Setting                                      | What the install does                                                                                                                                                                                                                                      |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Client Portal** Notification Type          | Creates it, and adds it to the email preferences in every existing user's **Notification Settings**. Users created later get it by default.                                                                                                                |
| **Portal Settings**, **Portal Menu**         | Unticks **Enabled** on ERPNext's own **Projects** row (route `/project`), so the portal menu lists **Projects** once.                                                                                                                                      |
| **Portal Settings**, **Default Portal Home** | Sets it to `/projects`, so customers land on their projects after signing in. It does this when the field is empty or points at ERPNext's `/project`. If the site already has another Default Portal Home, the install leaves it alone; change it by hand. |
| **Website Settings**, **Route Redirects**    | Removes a redirect from `projects` to `project` if the site has one. Other redirects stay.                                                                                                                                                                 |

The install saves a setting only when it changes something, and running it again changes nothing. Afterwards the settings are yours: re-tick the `/project` row or pick another home page and later migrations leave your choice in place.

Sites that had the app before this set-up ran at install get it once from a patch, `erpnext_taskview.patches.v1_0.setup_client_portal`, the next time `bench migrate` runs. The patch and the install run the same code. (Frappe's `install-app` marks every patch of a new app as done without running it, so on a new site the install, not the patch, does the set-up.)

## Allow overlapping time logs

Task View's timers overlap by design. A paused timer keeps the time it started, and stopping it logs its hours from that time, so a timer you paused to run another ends up with a time log that overlaps the other one. ERPNext refuses a Timesheet whose logs overlap for the same user or Employee unless Projects Settings tells it not to check. With the checks on, stopping the timers still works, but the next timer you start on that project and submitting the Timesheet both fail with "Row …: From Time and To Time of … is overlapping with …".

In **Projects Settings**, tick both:

- **Ignore User Time Overlap**
- **Ignore Employee Time Overlap**

The app does not change these settings for you, and both are unticked in a new ERPNext site.

> [!NOTE]
> Since ERPNext 16.51.0 the user check applies to every Timesheet, because ERPNext now fills in the Timesheet's user (the Employee's user, or else whoever created it). Before that, Timesheets without an Employee were never checked for overlap, so a site that ran Task View fine on an older ERPNext can start hitting this error after an upgrade.

## Check the install

1. In the desk, open **Project** or **Task** in list view. It opens as Task View. The view menu next to the title also offers **List**.
2. Start a timer on a task: the timer dock appears on the desk. See [Timers and timesheets](task-view/timers.md).
3. Sign in as a customer who has access to a project and open `/projects`. See [Giving customers access](client-portal/administering-access.md).

If `/projects` shows no portal, check that `apps/erpnext_taskview/erpnext_taskview/www/projects.html` exists, and run `bench build --app erpnext_taskview` again.

## Upgrade

Update the app the way you update any Frappe app: `bench update`, or pull the new code in `apps/erpnext_taskview` and then run these from the bench directory.

```bash
bench --site <SITE_NAME> migrate
bench build --app erpnext_taskview
```

`bench migrate` re-syncs the custom fields and property settings and creates the Client Portal Notification Type if it is missing. It also runs any new patch the app has shipped since you last migrated, including the portal set-up for a site that had the app before the install did it: see [What installing sets up](#what-installing-sets-up).

After upgrading ERPNext to 16.51.0 or later, check that both overlap settings in **Projects Settings** are ticked: see [Allow overlapping time logs](#allow-overlapping-time-logs).

## Uninstall

```bash
bench --site <SITE_NAME> uninstall-app erpnext_taskview
```

Frappe asks you to confirm and takes a backup of the database first, unless you pass `--no-backup`. It then deletes what belongs to the app's module, ERPNext TaskView: the custom fields (**Budgeted Hours** on Project, the four timer fields on Timesheet Detail, **Pinned** on ToDo) and the property settings, so Task and Project open as an ordinary list again. The app has no DocTypes of its own, so no table is dropped. The bundles, the `/projects` portal, its menu entry and the `/project` redirect come from the app's hooks and stop with it.

These stay behind:

- Your projects, tasks and Timesheets, including every time log a timer wrote. Rows of a timer that was still open stay as rows with no To Time.
- Frappe does not drop database columns when it deletes a custom field, so the values of **Budgeted Hours** and the timer fields stay in the database, out of sight.
- Pins are ToDos, so each pinned task stays assigned to the person who pinned it.
- The **Client Portal** Notification Type and the notifications it carried.
- The portal settings the install changed: **Default Portal Home** still reads `/projects`, which no longer exists, and ERPNext's own **Projects** row in **Portal Menu** stays unticked. Change both in **Portal Settings** if customers still use the portal.
